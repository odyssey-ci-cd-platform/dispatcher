## Summary

The audit-1 fix pass was diligent: 13 of 21 findings are fully fixed and the other 8 are partly fixed.
Two of the fixes introduced Critical regressions that the tests lock in rather than catch: step timeouts and run cancellation no longer stop a running step, and a failed step no longer stops its job.

The event envelope, stream names, and payload keys that other services consume exist only as internal Go types, with no published contract.

## New findings

### AUD-022 — Step timeouts and run cancellation do not stop a running step

- **Severity:** Critical
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/runner/docker.go:235-246`, `internal/runner/docker.go:369-372`
- **Problem:** Per-step timeouts exist "to bound long-running/non-terminating processes", and README's teardown principle assumes a cancelled run ends. Neither holds. `execCommand` blocks in `stdcopy.StdCopy` on the attached exec stream until the process exits, whatever its context says. gh-73 removed the select that used to return at the deadline (see Corrections). The step-timeout and cancellation tests use `sleep 5` / `sleep 10`, which end on their own, and they assert only the error text, never how quickly `Run` returned.
- **Failure scenario:** A step `sleep 20` with `timeout = 1000` returned after 24.7s with a step duration of 20.06s (measured). A run cancelled 0.5s into `sleep 20` returned 19.8s after the cancel. Consequences: a step `sleep infinity` (or a hung test) with a timeout never finishes; the gRPC client's `-timeout` frees nothing on the server; the container stays up until the process dies (AUD-001); partial output is discarded because the `StdCopy` error path returns empty buffers.
- **Suggested fix:** On context done, close the hijacked connection and kill the exec'd process (or the container, since the job ends anyway), then return. Keep whatever output arrived. Assert in tests that `Run` returns within the timeout plus a small margin.

### AUD-023 — A failed step no longer stops its job; later steps keep running

- **Severity:** Critical
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/runner/docker.go:256-280`
- **Problem:** After gh-65, a non-zero exit returns a nil error, and the `runSteps` switch exits only on `runErr`, so the loop proceeds to the next step. Before gh-65 the run error stopped the loop (`7d7be54:internal/runner/docker.go:256`). The behavior change was not recorded anywhere, contradicts the fail-fast principle README applies between stages, and has no test: every failing-step test has a single step.
- **Failure scenario:** Steps `test` (`exit 3`) then `deploy` (`echo DEPLOYED`): the job is Failed, and `deploy` ran and printed `DEPLOYED` (measured). Code that fails its tests gets deployed in the same job.
- **Suggested fix:** Stop the job at the first non-zero step exit (and record later steps as Skipped if the result model should show them). If continue-on-error is ever wanted, make it an explicit per-step key. Add a two-step test.

### AUD-024 — The in-process results recorder shards history as soon as two servers share a bus

- **Severity:** Critical
- **Category:** architecture
- **Verification:** Confirmed
- **Location:** `cmd/server/main.go:57-89`, `docs/adr/0002-results-db-technology.md` (Decision 1; When to revisit), `README.md` (Server environment variables, `ODYSSEY_RESULTS_DB`)
- **Problem:** ADR 0002 binds "one writer: a `results-recorder` consumer", and README says "the server's in-process recorder is the only writer". The recorder starts inside every server that has `ODYSSEY_REDIS_ADDR` set, against a local SQLite file, as consumer group `results-recorder`. Nothing in the code or docs prevents a second server from joining the same bus. When one does, consumer-group semantics deal each event to exactly one server, so each database holds a random subset of every run. The recorder's parent-row check then fails for events whose parent landed elsewhere, and those events retry for about 25 minutes before dead-lettering. ADR 0002's own revisit trigger is "a second engine instance needing the same DB → Postgres", and running more than one engine is exactly the deployment shape this repository's issue tracker plans for (issue #35).
- **Failure scenario:** Two recorders (`node-a`, `node-b`) in group `results-recorder`, with 20 runs of `pipeline.started` / `job.started` / `pipeline.finished` published (measured): node a stored 12 runs (9 finished, 9 jobs), node b stored 8 runs (7 finished, 8 jobs); 4 runs' final status was lost and 3 job events sat pending toward dead-letter.
- **Suggested fix:** Run the recorder as its own single-instance process (`cmd/results-recorder`) instead of inside the server, or take the documented Postgres growth path. Record the decision in ADR 0002. Until then, refuse to start the in-process recorder when the group already has another live consumer (`XINFO CONSUMERS`).

### AUD-025 — The recorder silently drops and overwrites history

- **Severity:** High
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/results/store.go:113-121,138-150,189-191`, `internal/results/migrations/00001_init.sql:34`, `internal/config/models.go:79-89`
- **Problem:** Validation allows duplicate step names within a job. Steps are unique on `(job_id, name)` with `ON CONFLICT DO NOTHING` and a name-keyed `UPDATE`, so a later step overwrites an earlier one. `pipeline.finished` and `job.finished` for an unknown parent run `UPDATE … WHERE` against zero rows and return nil, contrary to the package doc ("Events missing their run identity fail loudly") and ADR 0002 decision 4. Meanwhile `step.*` events for a job whose `job.started` failed to emit error out and dead-letter after about 25 minutes. Emission failures are allowed by ADR 0001's degradation policy. The steps table records no timestamps and no error text.
- **Failure scenario:** Measured: two steps named `test`, the first `failed`/exit 1 and the second `passed`/exit 0, leave one row, `test passed 0`, so the failure is erased from the history ADR 0002 says flakiness detection will read. Also measured: `job.finished` with no prior `job.started` returns nil, and the job's final status is silently lost.
- **Suggested fix:** Reject duplicate step names at validation, or key steps by ordinal. Check `RowsAffected` and fail events that match no row. Add `started_at`/`finished_at` and an error column to steps.

### AUD-026 — Large step output makes the whole result undeliverable; output is buffered unbounded

- **Severity:** High
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/runner/docker.go:369-372`, `internal/server/mapping.go:32-44`, `cmd/client/main.go:30-32`, `api/v1/odyssey.proto:63-66`
- **Problem:** Every step's stdout and stderr are held in memory in full, and the entire pipeline's output is returned in one unary response. gRPC clients reject messages over 4 MiB by default, and neither the bundled client nor any documented setting raises the limit. A test suite that prints a few MiB is ordinary. Concurrent jobs multiply the memory held in the server.
- **Failure scenario:** Measured: a job whose step printed 5 MiB → the pipeline ran to completion on the server and the client got `ResourceExhausted: grpc: received message larger than max (5242951 vs. 4194304)`, with no statuses and no results. A step that prints without bound (`yes`) grows the server's memory until it is OOM-killed.
- **Suggested fix:** Cap retained output per step (tail-keep with a truncation marker). Return results by streaming RPC or by reference (run id plus the results DB). Set explicit message-size limits on both ends.

### AUD-027 — Execution security posture is not production-safe

- **Severity:** High
- **Category:** security
- **Verification:** Confirmed (govulncheck, code reading)
- **Location:** `internal/runner/docker.go:149-159`, `cmd/server/main.go:58`, `go.mod` (`golang.org/x/net v0.58.0`)
- **Problem:** Pipelines are untrusted code, but jobs run as the image's default user (usually root) with no memory, CPU, or pids limit and default bridge networking. The server needs the Docker socket, which makes it root-equivalent on its host. Redis is reached with only an address: no password, ACL, or TLS. Every lifecycle event and dead-letter flows through it. `govulncheck` finds four vulnerabilities reachable from the gRPC server (GO-2026-6617, GO-2026-6612, GO-2026-6611, GO-2026-6603: HTTP/2 crash, flow-control, CPU, and memory exhaustion), all fixed in `golang.org/x/net@v0.60.0`.
- **Failure scenario:** One pipeline step `:(){ :|:& };:` exhausts the host's process table for every other job. A crafted HTTP/2 client can crash the server.
- **Suggested fix:** Bump `golang.org/x/net` and add `govulncheck` to CI. Set default container limits and a non-root user policy. Support Redis auth and TLS through configuration.

### AUD-028 — Results misreport timeouts, env-file faults, and skipped stages

- **Severity:** Medium
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/runner/docker.go:265-271`, `internal/runner/docker.go:284-293`, `internal/orchestrator/orchestrator.go:103-110`
- **Problem:** A timed-out step is recorded with a fabricated `ExitFailure` (1), no `Err`, and empty output. It is indistinguishable from `exit 1`, and the timeout text goes only to the log and to a run error that the gRPC mapping drops (AUD-004). When the env file cannot be read after a step, a second `StepResult` with the same name is appended and a second `step.finished` is emitted, so the result shows the step both passed and errored, and the recorder's name key makes the later write win (AUD-025). Under fail-fast, stages after the failing one are simply absent from the result and emit no events; the result model has `StatusSkipped` but never uses it.
- **Failure scenario:** Measured: `sleep 5` with `timeout = 1000` → `exit=1 status=failed stdout="" stepErr=<nil>`. Measured: step `rm -f "$ODYSSEY_ENV_FILE"` → two results, `rm exit=0 passed` and `rm exit=-1 errored`.
- **Suggested fix:** Give timeouts their own representation (`ExitNone` plus a timeout error, or a dedicated status). Attach an after-step env read failure to the same step result. Emit Skipped results and events for unexecuted stages.

### AUD-029 — `CreateTar` drops symlink targets and buffers the whole project per job

- **Severity:** Medium
- **Category:** correctness
- **Verification:** Confirmed
- **Location:** `internal/common/utils.go:51`, `internal/common/utils.go:34-36`
- **Problem:** `tar.FileInfoHeader(info, "")` writes symlinks with an empty `Linkname`, so every symlink in a project arrives in the container broken. Common cases are `node_modules/.bin`, Python virtualenvs, and versioned shared libraries. The archive of the whole tree, `.git` and build output included, is built in memory once per job, so N concurrent jobs of one pipeline hold N copies.
- **Failure scenario:** Measured: a directory with `link.txt → real.txt` produces a tar entry `link.txt type=2 linkname=""`.
- **Suggested fix:** Read the link with `os.Readlink` and pass it to `FileInfoHeader`. Stream the tar through an `io.Pipe` into `CopyToContainer`. Consider an ignore list.

### AUD-030 — Per-job overhead and unbounded concurrency

- **Severity:** Medium
- **Category:** performance
- **Verification:** Plausible
- **Location:** `internal/runner/docker.go:69,124-137,216,284,338`, `internal/orchestrator/orchestrator.go:135-167`, `cmd/server/main.go:103`
- **Problem:** Every job calls `ImagePull` even when the image is local, which costs a registry round trip, consumes Docker Hub's anonymous pull-rate budget, and fails offline. README says "Docker already handles local image caching", but the forced pull bypasses that cache. Every step costs two extra execs (`cat` of the env file before and after). The project is tarred once per job. The jobs of a stage all start at once, with no limit, and the gRPC server accepts unlimited concurrent `RunPipeline` calls. The runner suite takes about 70s, mostly container churn.
- **Failure scenario:** A 20-job stage starts 20 containers at once, makes 20 registry calls, and builds 20 project tarballs. On a shared egress IP, Docker Hub rate limits turn into `failed to pull image` Errored jobs.
- **Suggested fix:** Pull only when the image is missing locally (or by policy). Read the env file once per step, after it runs. Bound job concurrency per server and RPC concurrency per server.

### AUD-031 — Server lifecycle gaps

- **Severity:** Medium
- **Category:** correctness
- **Verification:** Plausible
- **Location:** `cmd/server/main.go:69,79,84-88,99,106-118`
- **Problem:** If the in-process recorder's `Run` returns an error, the server keeps serving without recording. That contradicts the startup rule on the same lines ("a server that cannot record history must not pretend it will"). `os.Exit(1)` after `defer` registration skips closing Redis and the results store. `GracefulStop` has no deadline and cancels no in-flight run, so a long pipeline blocks shutdown until a supervisor sends SIGKILL, which leaks containers (AUD-001). SIGINT/SIGTERM are subscribed twice, once by `NotifyContext` for the recorder and once by a channel for the gRPC server, so the recorder stops while in-flight runs are still emitting.
- **Failure scenario:** The recorder fails on a persistent Redis error. Hours of runs succeed but never reach the results DB, and the only trace is one log line.
- **Suggested fix:** Use one signal context. Treat recorder exit as fatal (or as a readiness failure). Bound graceful stop and cancel runs after it. Return errors from a `run()` function so defers execute.

### AUD-032 — Event delivery is best-effort at the producer and lossy at the stream

- **Severity:** Medium
- **Category:** architecture
- **Verification:** Plausible
- **Location:** `internal/orchestrator/orchestrator.go:41-50,146-153`, `internal/runner/docker.go:304-311`, `internal/bus/bus.go:22-24,45-50`
- **Problem:** ADR 0001 makes the bus the real-time channel and ADR 0002 makes it the only feed of the system of record. But producers drop an event after one failed `XADD` ("logged, never fatal"). `MAXLEN ~100000` trimming deletes entries whether or not every consumer group has read them, so a recorder that is down long enough loses history permanently, and `odyssey:dead` has no bound at all. Nothing documents which consumers may rely on seeing every event; the recorder's design assumes it will.
- **Failure scenario:** A Redis blip while one job finishes: `job.finished` is never written, the run's job stays `pending` in the results DB forever, and any consumer that waits on `job.finished` waits forever.
- **Suggested fix:** Retry terminal events (`*.finished`) with bounded backoff before giving up. Size trimming against the slowest required group (or trim by `MINID` after the recorder acks). Document the delivery guarantee per event type in the event contract (AUD-033).

### AUD-033 — The interfaces other services consume have no published contract

- **Severity:** Medium
- **Category:** architecture
- **Verification:** Confirmed (by code reading)
- **Location:** `internal/domain/event.go:5-28`, `internal/bus/bus.go:14-25`, `internal/runner/docker.go:318-333`, `internal/orchestrator/orchestrator.go:142`, `internal/results/migrations/00001_init.sql`, `docs/adr/0002-results-db-technology.md` (Decision 5)
- **Problem:** This repository publishes three interfaces to other services: the event envelope on `odyssey:events` (type names, fields, payload keys such as `stage`, `status`, `exit_code`, `duration_ms`, status slugs), the dead-letter stream shape, and the results-DB schema that ADR 0002 says analytics services "query directly on day one". The envelope is defined in an `internal` package that no other module can import. Payload keys exist only as string literals at the emit sites. The only description is scattered across CHANGELOG entries and doc comments. No document states which fields are required, which are optional, or how the shapes evolve, and no test pins the wire shape. The gRPC API is the only interface with a schema (`api/v1/odyssey.proto`).
- **Failure scenario:** A rename of a payload key, or of `omitempty` on `run_id`, compiles, passes every test in this repository, and silently breaks every consumer outside it.
- **Suggested fix:** Add `docs/contracts/` with the event envelope, payload keys per type, delivery guarantees, dead-letter shape, and results-DB read schema. Back it with a machine-readable schema (JSON Schema or protobuf messages in a public package). Add golden-file tests that pin the serialized shapes, so any change is a deliberate contract revision.

## Strengths

- The audit-1 response was thorough and well documented: one issue per finding, every fix cites its finding ID in code comments, and the CHANGELOG and README record each decision.
- The event-bus consumer is solid: validated construction, backoff, cursor-driven claim recovery, immediate dead-lettering of poison entries, and at-least-once semantics stated as the handler contract.
- `scripts/e2e-event-bus.sh` is a model integration test: it exercises live Redis, the real server, the client, and the subscriber, asserts the results DB, and cleans up on pass and on fail.
- ADRs 0001 and 0002 weigh real alternatives and name explicit revisit triggers.
- One `make check` gate (vet, tests, tidy, gofmt) behind protected `main`, SHA-pinned actions, and `persist-credentials: false`.
- Config validation aggregates every violation, and unknown keys are now rejected.

## Recommended order

1. AUD-022, AUD-023: restore step-timeout enforcement and stop-on-failure in the runner, with tests that assert the intent (promptness, step skipping).
2. AUD-024, AUD-025: move the recorder out of the server process and stop silent history loss, before any history is relied on.
3. AUD-033 with AUD-032: publish the event and results contracts with their delivery guarantees, pinned by golden tests.
4. AUD-026 and AUD-004: bounded output and a result that carries its run id.
5. AUD-027 and AUD-005: dependency bump, govulncheck in CI, container limits, symlink-safe path confinement.
6. AUD-036 and AUD-035: one PR per issue, a required review, and a stronger CI gate so the next fix pass cannot regress silently.
